# 公众号写作指南

本指南负责表达质量；事实、主张、个人材料和审稿门槛以 `editorial-workflow.md` 为准。目标是
写出准确、有判断、对读者有用且适合手机阅读的文章，不是欺骗 AI 检测器。

## 内容优先级

按以下顺序解决冲突：

1. 事实与证据边界。
2. `brief.yaml` 定义的读者问题、核心判断和交付。
3. 用户本轮明确要求。
4. 经确认适用于本类型文章的 `playbook.md` 规则。
5. persona 的表达偏好。
6. 本指南的通用建议。

人格、模板和流行写法都不能覆盖事实，不得为了风格编造作者经历、人物、对话、场景、数字或
引语。资料不够时缩小主张，不把空白填成“合理细节”。

## 开头与结构

### 开头

在前 3–4 段完成至少两件事：

- 说清读者面对的具体问题或冲突。
- 给出文章核心判断，或解释为什么暂时不能下结论。
- 让读者知道继续阅读能得到什么。

不要用“在当今时代”“随着科技发展”“这是一个值得深思的问题”铺垫。没有用户亲历材料时，
从公开事实、观察、问题或判断开场，不写虚构的凌晨、办公室、咖啡馆或朋友对话。

### 章节

- 每个 H2 只承担一个推进任务，并对应 `brief.sections` 和至少一个 `claim_id`。
- 段落不是越短越好。复杂解释允许更长，关键判断可以单独成段。
- 结构按论证需要变化，不要求每节机械使用“观点 → 例子 → 总结”。
- 结尾交付 `goal.takeaway` 或 `goal.action`；不必强行升华，也不必故意戛然而止。

优先选择能解决问题的框架：

- 痛点/清单文补齐步骤、条件、成本、风险和失败信号。
- 对比文先统一标准，再给“什么情况下选什么”。
- 热点/观点文写出共识、分歧、证据边界和新增判断。
- 故事/复盘文只使用用户材料或可靠来源明确记载的真实细节。

## 事实、推断与引用

- 每一个具体数字、日期、引语、研究结论和时效性事实，都要能对应 `claims.yaml` 与
  `sources.yaml`。
- 直接引语必须逐字核对；无法逐字核对时使用转述并标明来源。
- `fact` 写事实，`inference` 明确“这意味着 / 我的推断是”，`opinion` 明确归属。
- 来源只支持局部结论时，不把它扩展成行业共识或因果关系。
- 不虚构搜索量、阅读量、榜单、百分比、专家身份和“业内人士透露”。
- 使用当前信息时写清口径和日期；来源相互矛盾时呈现差异，不擅自挑一个当真相。

不是每个 H2 都必须塞数据。解释、判断和行动建议可以没有外部数字，但其中的具体事实仍要有
证据。引用的作用是支持主张，不是制造“资料很多”的表象。

## 账号声音

读取 `style.yaml`、对应 persona 和有效的 `playbook.md`。使用它们控制：

- 语气浓度：克制、温暖、锐利或口语化。
- 术语密度：读者能否理解，是否需要解释。
- 判断方式：先给结论、先给证据，或先交代问题。
- 不确定性表达：哪里有把握，哪里只是推断。
- 收束方式：行动、影响、判断框架或开放问题。

Persona 只是偏好，不是内容生成器：

- `opening_style: scene/personal_moment` 只有在用户提供真实场景时使用，否则改为观察或判断。
- 第一人称可以表达观点，不能凭空表达经历。
- 不从 persona 示例复制数字、人物或句子。
- 不为了“更像某人”模仿可识别作者的独特句式或大段表达。

## 语言与节奏

### 直接表达

优先使用具体名词和动词，删除不推进论证的套话。常见风险包括：

- 空过渡：“值得注意的是”“不可否认”“众所周知”。
- 空总结：“未来可期”“让我们拭目以待”“这值得每个人深思”。
- 空强度：“极其重要”“颠覆性”“史诗级”，却没有说明重要在哪里。
- 假共识：“大家都知道”“业内一致认为”，却没有来源。

这些表达不是无条件禁词；只有它们准确、有归属、能推进文章时才保留。

### 自然节奏

- 让段落长度服务内容密度，避免连续多段长度和句式完全相同。
- 关键判断可以短，复杂证据要解释完整。
- 转折应来自论证，不为制造“人味”随机跑题或自我打断。
- 口语词、破折号、括号和单句段落按 persona 少量使用，不设数量配额。
- 保留必要的犹豫与边界，但不为显得真诚重复“我也不知道”。

不要故意制造语法错误、不完整句、虚假时间地点、无关细节或情绪起伏。机械“人味”分只能定位
可能的套话、节奏过齐和信息密度问题，不能证明作者身份。

## 移动端排版

正文完成后读取 `layout-playbook.md`：

- 用模块解决 attention、readability、memorability 或 conversion 中的真实问题。
- 一篇文章通常只需少量高价值模块；不为“丰富”堆叠卡片。
- `callout` 用于确有必要抬高的提醒，`timeline` 用于真实时间序列，`quote` 用于可核验引语，
  `summary` 用于帮助读者复述结论。
- 没有足够内容填满模块时，使用普通正文。
- 表格在手机端尽量不超过 4 列；复杂对比拆成卡片或小节。
- 连续大段纯正文影响阅读时，用小标题、列表、图表或段落拆分解决，不用装饰模块掩盖结构问题。

图片引用必须有准确 alt；正文图应紧跟解释它的图例。只在图片能解释、对比或建立情境时使用，
不按固定字数插图。

## 编辑锚点

只有缺少用户个人判断，而加入真实观点会显著改善文章时，才保留 1–2 个编辑锚点：

```markdown
<!-- ✏️ 编辑建议：补一句你在这个问题上的真实判断或经历；没有就删除本注释。 -->
```

锚点不是交付质量的替代品。发布前必须删除所有 HTML 注释；用户没有材料时，文章也要作为一篇
无虚构、可独立阅读的成稿成立。

## 交付前自检

### 内容

- [ ] 文章回答了 `audience.question`，结尾交付了 `goal.takeaway/action`。
- [ ] 核心判断、最强反方和适用边界清楚。
- [ ] 每个具体事实都能对应已核验来源；推断和意见有明确归属。
- [ ] 没有编造作者经历、人物、对话、场景、数据或引语。
- [ ] 没有 `unsupported` 主张进入正文。

### 表达

- [ ] 开头尽快进入问题或判断，没有空泛铺垫。
- [ ] 每节各有任务，无重复论点和无关段落。
- [ ] 语言符合 style/persona，但没有被模板绑架。
- [ ] 段落节奏自然，既不整齐到机械，也不故意破坏语法。
- [ ] 标题准确，不用虚构数字、身份或结果制造点击。

### 产物

- [ ] 初稿保存在 `draft.md`，通过后的成稿保存在 `article.md`。
- [ ] `brief.yaml`、`claims.yaml`、`sources.yaml` 与正文一致。
- [ ] `generated/review-report.json` 与 `draft-metadata.json` 的编辑状态一致。
- [ ] 发布前已删除 HTML 注释，引用图片和图例均可解析。
